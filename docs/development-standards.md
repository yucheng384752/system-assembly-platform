# 開發與文件標準

本專案後續檔案需遵守 `C:\Users\gslab\Desktop\clean_code 驗證.txt`
中的 clean code 準則。此文件作為專案內部落地版規範。

## 語言規範

- 必要文件使用繁體中文撰寫。
- 技術識別字、檔名、API path、程式碼名稱可保留英文。
- 面向非技術使用者的 GUI 文案需以業務語言描述，不直接暴露不必要的技術細節。

## 命名

- 使用有意義且可搜尋的名稱。
- 避免誤導性命名。
- 避免只用數字、字母或模糊縮寫做區分。
- 類別名稱使用名詞，函數或方法名稱使用動詞。
- Kit、recipe、manifest 的命名需能反映業務能力。

## 函數

- 函數應保持簡短，理想上不超過 20 行。
- 每個函數只做一件事。
- 一個函數內只維持同一抽象層級。
- 參數數量盡量不超過 3 個。
- 避免隱藏副作用。
- 使用描述性的函數名稱表達意圖。

## 註解

- 優先用清楚的程式碼表達意圖。
- 不用註解彌補難讀的程式碼。
- 可接受的註解包含法律資訊、TODO、警告、重要脈絡說明。
- 避免多餘、誤導、流水帳式註解。

## 格式

- 相關程式碼應靠近。
- 用空行分隔不同概念。
- 行寬維持在合理範圍。
- 遵循專案既有格式，不製造不必要的風格差異。

## 物件與資料結構

- 物件應隱藏資料並暴露操作。
- 資料結構可暴露資料，但不混入複雜行為。
- 遵循最少知識原則。
- 避免同一結構同時承擔物件與資料結構兩種角色。

## 錯誤處理

- 使用例外處理，不以錯誤碼取代例外。
- 提供有意義的錯誤訊息。
- 避免返回或傳遞 `null`。
- 將錯誤處理與業務邏輯分離。

## 邊界

- 第三方程式碼應透過包裝層隔離。
- 對重要第三方 API 建立學習性測試或驗證腳本。
- 外部工具、target system、GUI composer、assembly engine 之間需維持清楚邊界。

## 測試

- 測試程式碼與產品程式碼同等重要。
- 測試需符合 FIRST 原則：快速、獨立、可重複、自我驗證、及時。
- 每個測試只驗證一個概念。
- 測試需保持乾淨且可讀。

## 類別與模組

- 類別與模組應保持簡短。
- 遵循單一職責原則。
- 維持高內聚、低耦合。
- 對擴展開放，對修改封閉。

## 系統設計

- 將建構與使用分離。
- 優先使用依賴注入。
- 擴展系統時保持架構簡潔。
- Kit composer 的核心邊界為：manifest、recipe、resolver、preview、assembly。

## 重構

- 小步重構，配合測試保護。
- 遵循童軍規則：讓程式碼比接手時更乾淨。
- 優先消除重複程式碼、過長函數、過大類別與過多參數。

## GUI 設計定位

- GUI 以正式環境工具為目標，不以展示型 landing page 或一次性 demo 設計。
- 第一畫面直接提供可操作的系統選配流程。
- 介面需支援掃描、比較、選配、預覽與 recipe 輸出。
- 若需要參考範例網頁或競品畫面，需先提出並說明用途，再進行搜尋或引用。
